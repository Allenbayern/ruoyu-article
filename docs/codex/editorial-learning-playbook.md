# 若雨随影文章组写作经验与任务导向

更新：2026-09-14。本文是项目执行说明，不替代 Vault 内容边界、机器契约或发布授权。

> 若雨随影不是把影视新闻写长，而是借一个当下影视话题，写出观众愿意聊天、站队和转发的人物处境、关系冲突与现实情绪。

## 1. 选题从谈资出发

观众不一定关心抽象社会问题，但会关心：这个人物为什么这样选？这段关系为什么让人纠结？这个动作为什么像自己？这部老作品为什么今天还值得重看？影视新闻只是入口，文章价值落到人物、关系、选择、命运和现实映射上。

文章组目标是爆款概率优先，不为完成数量平均分配选题。日常默认两篇 Markdown 成品；材料不足时补证、换题或少交，不用弱题凑数。

每个候选先填写：明确读者、具体对象、核心问题、冲突或反差、可核验材料、读者收益、当前触发或常青理由，并检查历史同作品、同事件簇和相近标题。删掉今天的新闻节点后仍没有价值的题目，不进入写作。

## 2. 标题在正文之后包装

标题不是写作方向，也不是文章价值的预先承诺。发现层可以保留
`title_skeleton` 作为热榜/搜索信号，历史记录可以做标题近似去重，但这些内容不能
进入写作 brief、材料验收或正文输入。`reader_question` 是文章要回答的问题，
`reader_takeaway` 只能在成稿复核后填写。

正文先进入 `body_draft.md`，通过四项内容复核后才创建 `title_pack.json`。标题包最多
三条，也可以一条或零条；每条都必须引用现有正文 locator 和来源 locator。标题包只有
`selected`、`return_article`、`return_material` 三种结果；标题选定后还要生成绑定标题包
哈希的 `title-pack-review.json`。标题需要新增事实时回到正文复核或材料验收，标题阶段不
自动补写。

《小城之春》从“1948年的爱情为什么今天还会让人讨论”改为“入围多伦多：相爱的人，为什么还要留分寸”，是把泛问题落到关系选择。《披荆斩棘2026》从“打工人精神状态最容易出圈”改为“王传君部落发疯，像下班后的你吗”，是去掉未经证明的热度判断，补上节目、人物群体、动作和代入。两个例子只说明方向，不证明点击率规律。

## 3. 正文先回答读者问题

### 3.1 先判定文章文体，再决定抓什么材料

文章组不得把所有题目都写成同一种“资料驱动评论”。选题预检必须先填写
`article_mode`：

- `setting_observation`：只有官方简介、主创和制作资料时使用。正文写设定、关系机制、宣发观察和读者问题，不伪装成观后感。
- `viewing_commentary`：必须有真实观看材料或多篇独立评论。正文才可以写具体场面、动作、对白和观影感受。
- `reported_feature`：必须有采访、现场、人物原话或可核查的事件背景。正文以现场细节、行为和原话推进。
- `fact_explainer`：材料只有事实清单时使用，只做事实解释，不扩写人物心理和观众反应。

文体一旦确定，抓爬任务必须同步声明：

```yaml
article_mode: setting_observation
required_source_roles: [official_fact, mechanism]
minimum_scene_requirement: 0
minimum_direct_quote_requirement: 0
forbidden_claim_levels: [viewing_experience, audience_consensus, ending]
```

只有官方简介时，文章最多写到“设定观察”；没有正片、采访或独立评论，不能写成观后评论或报道。

### 3.2 搜索按四层材料分流

发现层只找信号和对象，不能直接喂给正文。定向搜索分成四层：

1. **事实层**：官方简介、档期、主创、制作信息；
2. **场面层**：正片、预告、具体动作和对白；
3. **采访层**：人物原话、现场行为、制作背景；
4. **反应层**：有范围和上下文的独立评论、观众反馈。

来源记录必须标明 `source_role`、`supports_mode` 和 `cannot_support`。一个官方简介不能自动支持具体场面、观后感或普遍口碑。

### 3.3 正文复核增加可读性问题

事实通过不等于文章成立。成稿还要检查：

- 开头是否先给体验、冲突、动作或具体对象；
- 每段是否增加新的事实、场面、关系、物件或判断；
- 是否把同一事实换成多个抽象说法；
- 删除“官方页面、来源、简介、材料、目前能确认”等元话语后，读者是否仍能复述文章判断；
- 读者面不写“剧集某月某日起在某平台播出”类播出日期/播出平台的通告句（用户偏好，2026-09-16；播出事件本身成为选题时除外）；
- 结尾是否回到开头的画面、问题或情绪。

若删掉来源说明后文章无法成立，结果为 `evidence_summary_disguised_as_article`，应补场面、补人物处境、改成更窄的设定观察，或退回选题。

开稿前只锁定对象、阅读问题、冲突、证据需求和解释机制，不锁定标题。正文要让读者
在没有 H1 的情况下仍识别对象、问题、解释和判断。首段必须用具体事实、场面或动作
开始；每个主要段落必须新增事实、场面、机制或判断。成稿复核后的
`reader_takeaway` 必须能回到正文 locator，相关事实还要能回到来源 locator。

标题包装只检查既有正文是否支持标题中的对象、动作、关系和事实，不反向要求正文补段。
标题复核只消费标题包和已有证据；标题和正文组合成 `delivery.md` 后，再做最终复核。

## 4. 正文要有材料，不只摆姿态

至少提供多种真实支撑：权威来源事实、具体人物/场面/动作、可追溯观点、由事实支持的分析，必要时标明猜测。每段应新增事实、动作、归属观点或有依据的分析；连续几段重复“真实”“共鸣”等判断，说明材料或主线不够，应补证、收窄或换题，不靠人生道理凑字数。

推荐结构：事实入口 → 人物或关系冲突 → 具体材料 → 现实代入 → 回到具体人物、作品或选择的可讨论判断。公众号版本要有明确影视对象、稳定判断、完整证据链和可收藏/转述的内容，不能变成泛社会评论或娱乐快讯。

## 5. 事实、观点和发现信号分开

热榜、标题、平台标签只能发现选题，不能证明观众普遍喜欢、已经出圈、人物真实动机、作品一定成功或某种情绪代表所有人。当前事实查权威来源；观众观点追溯评论上下文，单人表达不写成“网友都认为”。来源和证据放后台，正文保持自然，不写成审稿报告，不暴露内部核验过程。

新片、新节目和新闻按当前权威来源核验；老片分析围绕作品材料，不强行编造新闻由头。不能用未经证实的封杀、抑郁、热度或因果制造刺激标题。

## 6. 开稿最小检查

- 这篇到底在聊谁、哪段关系或哪种选择？
- 删掉今天的新闻节点后，文章还剩什么价值？
- 正文前 20% 是否已经出现具体对象、事实或场面？
- 读者看完后能不能用一句话转述给朋友？
- 每个主要段落是否确实增加信息，而不是换词复述？

## 7. 获得感写作闸门

2026-09-11，用户用微信对标稿指出：要的是有内容、读完有获得感的文章，不是把标题问题用不同句子再说一遍。对标篇的共同点是先钉死一个具体对象，再把对象讲清楚，例如演员年龄和剧照、原著口碑和预告气味、衣服长短和身份。它们不是更好的通稿，是读者能转述的文章。

动笔前先写下 3 条「读者读完能转给别人的硬信息」。写不出 3 条，就补材料或换切角，不准用关系感悟、标题复述、「不是A是B」填篇幅。

每段只新增一类信息：人名和身份、动作顺序、场面物件、制作数字、可核验争议。写完问一句：删掉这段，读者会少知道一件事吗？不会就删。

参考爆款只用于学习文体和节奏，不作为当前文章的事实来源。优先学习它们的具体对象、生活化转译、场面推进和情绪回收；不要照搬未经核验的情节、口碑、结局或夸张判断。

正文里的问题，用机制、场面或物件回答。禁止把问题改写成解释腔，例如「这不是后来才发生的转折」「靠的不是名分，是位置」「从前的婚约不能再用，眼前的日子还得过」。出品名单、奋力求生、按姓氏笔画、定档套话同样不进正文。标题只能在正文通过后从这些已成立的内容中包装出来。

字数服从材料。材料够就写够，不够就短。禁止为了凑 1000 字灌水。对标微信文章的信息密度，不对标它们的夸张判断，例如「一万个放心」「收视要爆」「网友都认为」。

微信正文通常抓不到全文时，仍以可核验事实包为准；参考篇标题只用于识别对象，不作为事实证据。不把对标篇的未核验情节、口碑或结局写进当前稿。

## 8. 对标文章先选形态，再配材料

2026-09-14 对用户提供的 9 篇《早春晴朗》微信文章做了正文级对比，证据见
`runs/2026-09-14/zaochun-reference-001/comparison-matrix.md`。它们不是同一种“爆款模板”：
有广告行业事实核查，有人物关系和结局动作链，有台湾/Netflix 的传播解释，有原著与剧版
的具体差异，也有基于观看场面形成的评论。共同点是首屏钉住一个具体对象和冲突，后文每段
继续增加读者能复述的事实、动作、物件、数字、原话或对照，结尾再把情绪收回到一个选择。

因此，候选卡、任务卡和写作 brief 必须先填写 `reference_shape`：

- `workplace_reality_check`：需要行业术语、工作流程、从业者经验或可核验的剧中错位；不能只写“职场很真实”。
- `relationship_plot_recap`：需要人物身份、动作顺序、关系转折和结果材料；没有结局授权就不能使用此形态。
- `audience_culture_explainer`：需要有范围的平台数据、地域/人群反应和可解释的类型或发行背景；单条评论不能代替人群证据。
- `adaptation_comparison`：需要原著与改编的对应段落、物件、情节或人物差异；标题和推荐文案不能代替原文核验。
- `viewing_commentary`：需要已观看的场面、动作、对白或多篇独立评论；只有简介时必须降为 `setting_observation`。
- `setting_observation`：只有官方设定、主创和简介时使用，写清设定机制和读者问题，允许短稿，不用感悟填充。

信息密集型形态的 `reader_gain_floor` 固定为 5，材料验收必须提供至少 5 条硬信息和 3
种具体支撑类型；`setting_observation` 保留至少 3 条和 2 种类型的兼容门槛。硬信息不是
“爱情很甜”“观众很上头”这类判断，而是人名与身份、时间与数字、动作顺序、场面物件、
行业事实、原著差异或范围明确的观点。每条要绑定来源定位，并在 `section_increments`
中说明它将让读者多知道什么。

写作前先做“材料形态匹配”：如果任务想写北漂/广告行业的真实感，就去找从业者经验和
具体工作细节；想写结局复盘，就去找已播集数、动作链和结果；想写出海，就去找榜单原文、
统计口径和市场背景；想写原著对照，就去找书中对应段落。只有平台简介时，不得借参考稿
的结局、观众共识、行业数据或夸张标题补洞，直接收窄问题或返回补证。

成稿复核增加三个硬问题：首屏是否兑现了 `opening_support_refs`；每个主要段落是否兑现
了一个 `section_increment`；删掉一段后读者是否确实少知道一件具体事情。任一答案是否定，
优先补材料或换角度，不能继续改写同一条抽象判断。

## 9. 修改、交付与效果记录

先修材料、主线和正文增量，再润色句子；标题只在正文通过后包装。同一问题修订一次仍不成立，就回到缺失材料或选题决策；不要继续换词直到检查变绿。交付时分别报告内容质量、爆款概率判断、事实风险和未验证项；爆款概率是可检验假设，不是保证。

沿用两篇、Markdown、1500–2200 通常目标及 1000–2700 接受带。`CONTENT_READY` 只有在标题选定、`title-pack-review.json`、最终复核和当前交付文件都通过后才产生；R8 治理和发布授权另行报告，不代发布。正文一旦改动，旧标题包立即失效，必须重新做内容复核；标题改动则只重做标题复核并更新交付文件、证据和 SHA-256。

发布后如能取得同口径曝光、点击、完读、转发、收益和 RPM，再按题材记录中位数和样本量。单篇偏好、模型评分和外部爆文不能直接升级为长期规律。

## 10. 成稿→L2 的工序顺序（2026-09-16 重排，P0）

L2 对抗复核绑定交付哈希，复核通过后任何正文改动都会让批准失效、需要重核一轮。
为避免一稿多轮，工序固定为：

1. 生成（正文 → delivery）；
2. 机器门禁全跑（claim-source、style_gate 含 fact_density、task-card fidelity、
   editorial protocol、preflight 五问等），全绿才往下走；
3. **读者面↔账本预检**（`scripts/ledger_coverage_precheck.py`：引号逐字核对 +
   LLM 缺口检查），发现的"读者面有、账本无"先修掉；
4. 人工偏好确认（controller 的写法偏好、禁区、发布边界——如播出通告句、字数）；
5. **最后才进 L2**，目标是 approval 一次过；小改动修复轮用增量复核
   （`codex_review --base-review`，diff-only + 抽查，基线哈希入库）；
6. final_review → content_delivery。

除非 controller 在 L2 之后提出新改动，否则 L2 每篇一轮即闭环；多轮是流程故障，
应在 RUN-RECORD §8 记录轮次与原因。

## 11. 封存与证据纪律（2026-09-17）

起因是一次真实事故：为演示扩展后的账本预检，直接在**已收尾且已发布**的
daily-008 上重跑，覆盖了 `review/art-001/ledger-coverage-precheck.json`
（无备份、不可还原）。此后固定四条：

1. **收尾即封存，自动生效**。`python -m article_group.close_out --run-root <run> --confirm`
   的最后一步写 `SEALED`（时间、署名、各篇交付哈希）。此后所有写证据的工具默认拒绝，
   退出码 2——不需要人再补一句"别再改了"。
2. **写证据一律走留底通道**。`article_group.evidence_write` 在覆盖前把旧文件存到
   `review/.before/<时间戳>/<路径>`，并往 `evidence-changelog.jsonl` 记一行
   （谁/何时/为什么/前后 SHA-256/是否 forced）。`restore()` 可按最近快照还原。
   已接入：账本预检、`evidence_rebind`、`title_freeze`、`wechat_render`、`close_out`
   （含它写的 `STEP-LOG.md`）、`final_review`、`run_record`、
   `scripts/record_controller_acceptance.py`（人工签字入口，带 `--force`）。
   仍绕过通道、只被运行时护栏兜住的写在
   `tests/test_runs_write_coverage.py` 的 `PENDING` 里逐条列名——那份名单过期或
   新写手未分类，测试就 fail。
3. **演练只在副本上做**。`python scripts/run_sandbox.py runs/<date>/<run-id>` 一条命令
   复制到 `/tmp`，副本内 `SEALED` 改名留痕、可自由写入，源 run 一字不动。
   演示、复现、工具试跑一律先建沙盘。
4. **"停"是自动的，"放开"要人点头**。改封存 run 只有两条路，都需 controller 明确指令：
   `--force` 直写（留底+记账，可还原）；或先 `unseal`（`SEALED` 改名为
   `SEALED.revoked.<时间戳>` 并记账，run 恢复可写），改完重新收尾再封存。
5. **护栏不靠记性**（2026-09-17 补）。`import article_group` 即装上进程级写入护栏
   （`article_group.runs_guard`，PEP 578 audit hook）：写/删/改名封存 run 内的路径一律
   抛 `SealedWriteBlocked`，唯一通道是留底通道的 `force` 与 `unseal`。
   `step-log.jsonl` / `evidence-changelog.jsonl` 按契约允许原地**追加**，重写/删除仍拦。
   覆盖范围是**进程内**：编辑器、`rsync`、`git checkout`、没 import 本包的脚本不在其内
   （那属于文件系统只读与全量哈希清单）。能写 run 的模块清单与"仍绕过留底通道"的欠账
   在 `tests/test_runs_write_coverage.py` 里维护——清单过期或新写手未分类，测试就 fail。
6. **封存 = 全量清单 + 可验证**（2026-09-17 补）。收尾写 `SEALED` 时同时写
   `SEALED.manifest.json`：逐文件 size+sha256，标记自身的字节哈希也一并记入。校验一条命令：
   `python -m article_group.run_seal --run-root <run>` —— 0 完好 / 2 有漂移 /
   3 无法验证（缺清单，例如封存时还没有本机制的 daily-008）。漂移会与
   `evidence-changelog.jsonl` 对照，分出**有账的 force 改动**与**无账的可疑改动**；
   append-only 文件按前缀校验（追加放行、重写算改动）。老 run 可用 `--backfill` 补录清单，
   但补录只能证明"补录之后未被改动"，不能证明封存时刻的内容——它会在清单里写明这一点。

配套的两条流水证据，每期都会自动生成，复盘时先看它们：

- `step-log.jsonl` / `STEP-LOG.md`：每个阶段的名字、起止、耗时、产物哈希，自动标出 ≥120 秒空档
  （daily-008 曾有 56 分钟无产物落盘，当时只能靠 mtime 反推）；
- `evidence-changelog.jsonl`：文件级写入流水，回答"这条证据被谁、何时、为什么改过"。
